## 1. Overview

### What this is

`sherin` is a self-hosted private workspace for generative media. Sign in with one Google account, write prompts, generate images through your configured inference path, and keep every asset in storage you control.

It is built for creators, artists, designers, and developers who want their own key, domain, and storage without a SaaS subscription, public gallery, credit system, or team account layer.

### Short version

Bring your own key, domain, and storage. Sherin gives you a polished single-owner generative media workspace with model-aware controls, a private gallery, a reusable reference archive, usage view, and storage adapters for Supabase Storage, Vercel Blob, Cloudflare R2, and AWS S3.

### Production lineage

Sherin demonstrates the lightweight starter boundary around BabySea execution patterns: product UI, owner-only Supabase Auth, provider switching, generation persistence, storage fallback, and deployment checks. It is intentionally simpler than BabySea's managed control plane and does not include billing or multi-tenant account management.

### Grounding rule

Public starter behavior is limited to the app implemented in this repository: Next.js App Router, Supabase Google OAuth, one-owner access control, Black Forest Labs or BabySea-backed image generation, generation records, storage adapters, optional Sentry runtime monitoring, optional cron processing, and Vercel/Netlify deployment. Billing, credits, provider marketplaces, multi-user teams, and managed BabySea hosting are out of scope.

### Adoption path

Deploy the starter, connect Supabase, configure Google sign-in, choose an inference path, choose a storage provider, run `pnpm run doctor`, and open `/access` with the email in `OWNER_EMAIL`. After your first image works, add a custom domain, alternate storage, Sentry, or cron processing if needed.

## 2. Stack contract

| Layer                | Required stack                                       | Runtime responsibility                                                                                 |
| :------------------- | :--------------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| Product runtime      | Next.js App Router + React                           | Render the public page, access flow, dashboard, Studio, Gallery, References, Usage, and Profile views. |
| Authentication       | Supabase Auth + Google OAuth                         | Allow exactly one configured owner email into the dashboard.                                           |
| Operational database | Supabase Postgres                                    | Store generation attempts, prompts, statuses, provider metadata, storage locations, and profile state. |
| Inference            | Black Forest Labs or BabySea                         | Generate images with server-only API keys and model-aware request fields.                              |
| Storage              | Supabase Storage, Vercel Blob, Cloudflare R2, AWS S3 | Save completed images, with Supabase Storage as the fallback path.                                     |
| Processing           | Next.js server actions/routes                        | Submit generation work, process queued/running jobs, and update records.                               |
| Observability        | Optional Sentry                                      | Capture runtime errors when a DSN is configured; run cleanly when it is absent.                        |
| Deployment           | Vercel or Netlify                                    | Host the app, auth callback, server routes, and optional cron entry point.                             |

No billing setup, credit ledger, team account system, provider marketplace, or public gallery is part of this starter contract.

## 3. Terminology

| Term               | Meaning in this starter                                                                                     |
| :----------------- | :---------------------------------------------------------------------------------------------------------- |
| Owner              | The single Google account allowed into the dashboard through `OWNER_EMAIL`.                                 |
| Studio             | Dashboard surface where the owner writes prompts, chooses models, adjusts settings, and starts generations. |
| Gallery            | Private archive of completed, failed, or unavailable generation records.                                    |
| References         | Private archive of stored input images that can be copied and reused in later generations.                  |
| Inference provider | `bfl` for Black Forest Labs, `babysea` for BabySea, or auto-detected from the configured API keys.          |
| Storage provider   | `supabase-storage`, `vercel-blob`, `cloudflare-r2`, or `aws-s3`.                                            |
| Storage fallback   | Supabase Storage save path used when a primary external storage provider is unavailable.                    |
| Processing route   | Server endpoint that can advance queued/running generation work, optionally protected by `CRON_SECRET`.     |

## 4. Boundaries

- Not a managed BabySea service or hosted SaaS product.
- Not a billing or credit-pack starter.
- Not a multi-tenant team workspace.
- Not a provider marketplace or model admin console.
- Not a public gallery or social sharing product.
- Not a replacement for Black Forest Labs or BabySea provider terms and keys.
- Not a storage migration service; you choose and operate your object storage.

## 5. Architecture

```text
Owner browser
  │ Google sign-in
  ▼
Supabase Auth -> owner email gate
  │
  ▼
Next.js dashboard
  │ Studio prompt + model settings
  ▼
Inference provider (BFL or BabySea)
  │ Completed image URL or bytes
  ▼
Storage adapter (primary provider, Supabase fallback)
  │
  ▼
Supabase Postgres generation record
  │
  ▼
Gallery, References, Usage, and Profile views
```

Sherin keeps secrets server-side. Browser code receives only public Supabase values and the authenticated owner session.

## 6. Quick start

### Deploy

Click **Deploy with Vercel** or **Deploy to Netlify** at the top of this README. Both buttons clone Sherin into your account and walk you through hosting settings.

Follow the setup order below from top to bottom. It matches [`.env.example`](.env.example): Config, Database & Auth, Inference, Storage, Observability, then Worker.

### Config

Set the exact URL where Sherin runs, then set the single Google account allowed into the dashboard:

```bash
NEXT_PUBLIC_SITE_URL=https://<your_domain>
OWNER_EMAIL=<owner_email>
```

For one-click deploys, you can start with the temporary `.vercel.app` or `.netlify.app` URL first. Update `NEXT_PUBLIC_SITE_URL` after you attach a custom domain.

### Database & auth

Create a Supabase project and set:

```bash
NEXT_PUBLIC_SUPABASE_URL=https://<supabase_project_id>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLIC_KEY=<supabase_public_key>
SUPABASE_SECRET_KEY=<supabase_secret_key>
```

Keep `SUPABASE_SECRET_KEY` private and never prefix it with `NEXT_PUBLIC_`.

Apply the database setup through either path:

- Supabase SQL Editor: open [`supabase/migrations/001_sherin.sql`](supabase/migrations/001_sherin.sql), paste it into the SQL Editor, and run it.
- Supabase CLI:

```bash
export SUPABASE_PROJECT_REF=<supabase_project_id>
pnpm supabase:link
pnpm supabase:push
pnpm supabase:typegen
```

In your Google Cloud console:

- Create OAuth 2.0 Client IDs for `Web application`.
- Add `https://<your_domain>` in `Authorized JavaScript origins`.
- Add `https://<supabase_project_id>.supabase.co/auth/v1/callback` in `Authorized redirect URIs`.
- Copy `Client ID` and `Client secrets`.

In your Supabase dashboard:

- Enable Sign in with Google.
- Fill `Client IDs` and `Client Secret (for OAuth)` from your Google Cloud console above.
- Add `https://<your_domain>` in `Site URL`.
- Add `https://<your_domain>/auth/callback` in `Redirect URLs`.

### Inference

Default: `bfl`. Allowed: `bfl`, `babysea`.

If `INFERENCE_PROVIDER=bfl`, fill the Black Forest Labs values:

```bash
INFERENCE_PROVIDER=bfl
BFL_API_KEY=<bfl_api_key>
BFL_API_BASE_URL=https://api.bfl.ai
```

If `INFERENCE_PROVIDER=babysea`, fill the BabySea values:

```bash
INFERENCE_PROVIDER=babysea
BABYSEA_API_KEY=<babysea_api_key>
BABYSEA_API_BASE_URL=https://api.us.babysea.ai
```

### Storage

Default: `supabase-storage`. Allowed: `supabase-storage`, `vercel-blob`, `cloudflare-r2`, `aws-s3`.

For the first deploy, keep Supabase Storage and the default quota:

```bash
STORAGE_PROVIDER=supabase-storage
CUSTOM_USER_STORAGE_QUOTA_GB=10
```

Fill provider-specific values only when you intentionally switch storage providers:

| Provider         | `STORAGE_PROVIDER` value | Required configuration                                                                                                                                             |
| :--------------- | :----------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supabase Storage | `supabase-storage`       | No extra values beyond Supabase.                                                                                                                                   |
| Vercel Blob      | `vercel-blob`            | `BLOB_READ_WRITE_TOKEN`; best when hosted on Vercel, smoke-test when hosted elsewhere.                                                                             |
| Cloudflare R2    | `cloudflare-r2`          | `CLOUDFLARE_R2_ACCOUNT_ID`, `CLOUDFLARE_R2_ACCESS_KEY_ID`, `CLOUDFLARE_R2_SECRET_ACCESS_KEY`, `CLOUDFLARE_R2_BUCKET_NAME`, endpoint values, and a public read URL. |
| AWS S3           | `aws-s3`                 | `AWS_S3_REGION`, `AWS_S3_ACCESS_KEY_ID`, `AWS_S3_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET_NAME`, and a browser-readable URL in `AWS_S3_ENDPOINT_URL`.                    |

For Cloudflare R2, `CLOUDFLARE_R2_ENDPOINT_URL` must be the S3 API endpoint, not a public custom domain. `CLOUDFLARE_R2_CUSTOM_DOMAIN_URL` must be the bucket's public read URL, such as the R2 Public Development URL (`https://pub-<token>.r2.dev`) or a production custom domain. Supabase Storage stays as the fallback save path.

For AWS S3, `AWS_S3_BUCKET_NAME` is the bucket Sherin writes into, while `AWS_S3_ENDPOINT_URL` is the browser-readable image base URL Sherin saves for previews. For production, prefer a CloudFront distribution or custom media domain, for example `https://<cloudfront-domain>` or `https://media.example.com`. Direct S3 bucket URLs such as `https://<bucket>.s3.<region>.amazonaws.com` also work only when the bucket/object read policy allows browser access. Sherin derives the SDK write endpoint from this value when it is an S3 URL, so AWS does not receive a duplicated bucket host.

The IAM user behind `AWS_S3_ACCESS_KEY_ID` must be allowed to write objects inside the bucket. Object actions such as `s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject` use the object ARN (`arn:aws:s3:::<bucket>/*`), while `s3:ListBucket` uses the bucket ARN (`arn:aws:s3:::<bucket>`). For a smoke-testable setup, attach an identity policy like this and replace `your-bucket-name` with your bucket name:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SherinObjectAccess",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::your-bucket-name/*"
    },
    {
      "Sid": "SherinBucketList",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::your-bucket-name"
    }
  ]
}
```

That identity policy only lets Sherin write and verify objects with AWS credentials. Browser image previews need a separate public read path because the browser does not use `AWS_S3_ACCESS_KEY_ID`. If `AWS_S3_ENDPOINT_URL` points directly at an S3 bucket URL, disable bucket-level public-access blocks that reject public bucket policies, then add a bucket policy like this:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SherinPublicReadGeneratedImages",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::your-bucket-name/*"
    }
  ]
}
```

For private buckets, put CloudFront or another public domain in front of S3 and set `AWS_S3_ENDPOINT_URL` to that browser-readable URL instead. Keep `AWS_S3_BUCKET_NAME` set to the real S3 bucket name; do not change it to the CloudFront domain.

### Observability (optional)


Open <http://localhost:3012/access>, sign in with `OWNER_EMAIL`, and generate your first image.

## 7. Core capabilities

### Why it's different

Sherin is the no-billing, no-team-account starter for a private creative workspace. It focuses on a single owner, fast setup, flexible inference, and storage ownership instead of credit packs or marketplace routing.

### Owner-only workspace

- Public home and access pages are open.
- Dashboard routes require Supabase auth.
- Only the Google account matching `OWNER_EMAIL` can enter the dashboard.
- Profile and sign-out are included.

### Generation lifecycle

1. Owner opens Studio and selects an image model.
2. The form shows model/provider-compatible controls.
3. Uploaded or URL-based input images are copied into controlled storage before provider submission.
4. A server action submits the request with server-only provider keys.
5. Sherin records the generation and processes queued/running work.
6. Completed images are saved through the selected storage adapter.
7. Gallery, References, and Usage read the private generation record.

### Storage adapters

Sherin supports Supabase Storage, Vercel Blob, Cloudflare R2, and AWS S3. Supabase Storage is the default and fallback, so new images can still save when a primary external storage provider is unavailable. Uploaded or URL-based input images are stored as reference assets under `user-upload/<user_id>/<generation_id>/input-N.<ext>` before inference, which makes the References page durable and keeps provider-facing URLs under your storage boundary. Supabase Storage uses a private bucket with signed URLs; Vercel Blob, Cloudflare R2, and AWS S3 object URL visibility follows the selected provider, bucket, and custom-domain policy. AWS S3 images must be browser-readable through the configured bucket URL or custom domain.

### Workspace pages

| Page           | What it does                                                                     |
| :------------- | :------------------------------------------------------------------------------- |
| **Studio**     | Write prompts, pick models, adjust settings, and generate images.                |
| **Gallery**    | Browse the private image archive with success, failure, and storage details.     |
| **References** | Browse stored input images, copy reusable URLs, and verify reference storage.    |
| **Usage**      | Review output counts, favorite model, storage health, and last-attempt activity. |
| **Profile**    | View account details and sign out.                                               |

Available image models are defined in `lib/app-config.ts`, with direct BFL capabilities in `lib/inference/bfl/models.ts` and BabySea identifiers derived in `lib/inference/babysea/models.ts`.

| Model id                 | Studio label       | Notes                                                                       |
| :----------------------- | :----------------- | :-------------------------------------------------------------------------- |
| `bfl/flux-1.1-pro`       | FLUX 1.1 Pro       | Direct BFL dimensions, image prompt, prompt upsampling.                     |
| `bfl/flux-1.1-pro-ultra` | FLUX 1.1 Pro Ultra | Direct BFL aspect-ratio request, image prompt, prompt upsampling, raw mode. |
| `bfl/flux-2-pro`         | FLUX 2 Pro         | FLUX 2 direct BFL sizing and input image support.                           |
| `bfl/flux-2-max`         | FLUX 2 Max         | FLUX 2 direct BFL sizing and input image support.                           |
| `bfl/flux-2-flex`        | FLUX 2 Flex        | FLUX 2 input image support plus guidance, steps, and prompt upsampling.     |
| `bfl/flux-2-klein-4b`    | FLUX 2 Klein 4B    | FLUX 2 Klein direct BFL sizing and lower direct input image limit.          |
| `bfl/flux-2-klein-9b`    | FLUX 2 Klein 9B    | FLUX 2 Klein direct BFL sizing and lower direct input image limit.          |

The BabySea path uses the same Sherin model ids and loads model schema from the BabySea model library when `INFERENCE_PROVIDER=babysea`.

## 8. Production readiness

Sherin is a deployable starter, not a managed BabySea service. Treat this section as the production operating contract for a self-hosted private generative media workspace: every claim should map to implemented code, documented configuration, and a command or workflow you can run before release.

### Enterprise posture

| Area          | Control in Sherin                                                                                                                          | How to verify                                                                                               |
| :------------ | :----------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------- |
| Access        | Supabase Google OAuth plus the `OWNER_EMAIL` allowlist; dashboard routes require the signed-in owner session.                              | Sign in at `/access` with the owner account and confirm non-owner accounts are denied.                      |
| Data boundary | Generation records live in Supabase Postgres behind RLS; generated media and input references are written to the selected storage adapter. | Apply `supabase/migrations/001_sherin.sql`, generate an image, then inspect Gallery, References, and Usage. |
| Storage       | Supabase Storage is the default signed-URL fallback; external object URL visibility follows the selected provider policy.                  | Run `STORAGE_SMOKE_TEST=1 pnpm run doctor` against safe buckets before switching providers.                 |
| Execution     | BFL and BabySea provider keys stay server-side; queued/running work is advanced by server actions and routes.                              | Run `pnpm run doctor`, submit a generation, and confirm the record reaches a terminal status.               |

### Production deployment

Use separate environments for local, preview, and production. Each environment should have its own Supabase project or credentials, OAuth client settings, inference keys, storage credentials, Sentry project/environment label, and `CRON_SECRET` when cron is enabled.

For Vercel, use the one-click deploy for first setup or the included `Deploy` workflow for controlled releases. The workflow deploys on `v*` tags and supports manual `preview` or `production` dispatches. Configure `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, and `VERCEL_TOKEN` in the matching GitHub environment; when any required secret is absent, the workflow exits as a no-op instead of leaking partial deployment state.

For Netlify, the included `netlify.toml` builds with `pnpm build` and uses the Next.js plugin. Prefer Supabase Storage, Cloudflare R2, or AWS S3 on Netlify; if you intentionally use Vercel Blob outside Vercel, validate `BLOB_READ_WRITE_TOKEN` with the storage smoke test before relying on it.

After every environment change, run `pnpm run doctor` and then redeploy. After storage credential changes, run the storage smoke test before allowing real owner traffic.

### Monitoring

Set `NEXT_PUBLIC_SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_ENVIRONMENT` to enable runtime error capture. Leave them blank for local development or forks that do not use Sentry; Sherin no-ops cleanly without telemetry.

Set `SENTRY_ORG`, `SENTRY_PROJECT`, and `SENTRY_AUTH_TOKEN` only in build or CI secrets when you want source-map uploads and the Sentry Project Check workflow. The auth token is build/CI-only even though the DSN is browser-visible.

Operationally, watch these signals:

- Worker responses from `/api/generations/process`, especially 401, 429, and 500 responses.
- `x-request-id` values returned by the worker and attached to Sentry events.
- Jobs that remain queued or running longer than the provider polling budget and cron cadence.
- Storage fallback metadata in Gallery, References, and Usage, which can indicate primary storage drift.
- Sudden changes in provider error rates, retry scheduling, or unavailable images.

### Backup and disaster recovery

- Enable Supabase Point-in-Time Recovery or scheduled backups for generation records before production use.
- Periodically test a restore into a non-production Supabase project; untested backups are only hopeful files.
- Mirror object storage to a second region or cold storage if generated media is business-critical.
- Keep the `sherin-generations` Supabase bucket available even when another storage provider is primary, because it is the fallback path.
- Align database retention and object-storage lifecycle policies so records do not outlive their media or vice versa.
- Keep a private deployment runbook with provider account ids, OAuth client ownership, bucket names, cron location, and secret owners. Do not commit that runbook if it contains live deployment details.

### Secret rotation

| Secret family                                          | Rotate when                                                        | Minimum follow-up                                                |
| :----------------------------------------------------- | :----------------------------------------------------------------- | :--------------------------------------------------------------- |
| `SUPABASE_SECRET_KEY`                                  | Maintainer access changes, suspected exposure, or scheduled audit. | Update hosting secrets, redeploy, run `pnpm run doctor`.         |
| `BFL_API_KEY`, `BABYSEA_API_KEY`                       | Provider access changes, spend anomaly, or suspected exposure.     | Update the active env, redeploy, generate a test image.          |
| `BLOB_READ_WRITE_TOKEN`, `CLOUDFLARE_R2_*`, `AWS_S3_*` | Storage operator changes, bucket policy changes, or exposure.      | Run `STORAGE_SMOKE_TEST=1 pnpm run doctor`.                      |
| `CRON_SECRET`                                          | Cron runner changes, logs expose headers, or ownership changes.    | Update all callers atomically and verify the worker returns 200. |
| `SENTRY_AUTH_TOKEN`                                    | CI maintainer changes, source-map upload failure, or exposure.     | Run `pnpm sentry:check` or the Sentry Project Check workflow.    |
| Google OAuth client secret                             | OAuth owner changes, Google project changes, or exposure.          | Update Supabase Google provider settings and test sign-in.       |

Rotate immediately after any secret appears in a terminal transcript, chat, screenshot, issue, pull request, or generated media metadata.

### Troubleshooting

| Symptom                                    | Fix                                                                                                                                                                                                                     |
| :----------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sign-in works but access is denied         | Check that `OWNER_EMAIL` exactly matches your Google account email.                                                                                                                                                     |
| Supabase redirects to the wrong page       | Align `NEXT_PUBLIC_SITE_URL`, Supabase Site URL, and Supabase Redirect URLs.                                                                                                                                            |
| Image generation does not start            | Run `pnpm run doctor` and verify `INFERENCE_PROVIDER` plus the active API key.                                                                                                                                          |
| Gallery shows the wrong provider           | Check `INFERENCE_PROVIDER` and `STORAGE_PROVIDER`, then redeploy after changing environment values.                                                                                                                     |
| Cloudflare R2 upload fails                 | Use the Cloudflare R2 S3 API endpoint for `CLOUDFLARE_R2_ENDPOINT_URL`, and set `CLOUDFLARE_R2_CUSTOM_DOMAIN_URL` to the bucket public URL.                                                                             |
| AWS S3 upload falls back to Supabase       | Keep `AWS_S3_BUCKET_NAME` set to the S3 bucket, set `AWS_S3_ENDPOINT_URL` to the CloudFront/custom/public read URL, allow `s3:PutObject` on `arn:aws:s3:::<bucket>/*`, then run `STORAGE_SMOKE_TEST=1 pnpm run doctor`. |
| AWS S3 upload succeeds but image is broken | Add a public `s3:GetObject` bucket policy for `arn:aws:s3:::<bucket>/*`, or put CloudFront/custom public domain in front of the private bucket and use that URL for `AWS_S3_ENDPOINT_URL`.                              |
| Vercel Blob upload fails on Netlify        | Run the storage smoke test; host on Vercel or switch to Supabase Storage, Cloudflare R2, or AWS S3.                                                                                                                     |
| Image shows as unavailable                 | Generation succeeded but the stored file URL cannot be resolved; check storage credentials.                                                                                                                             |
| Jobs stay queued or running                | Open Studio, Gallery, References, or Usage to trigger processing, or configure cron for `/api/generations/process`.                                                                                                     |
| Worker returns 401 to cron                 | Send `Authorization: Bearer <CRON_SECRET>` and rotate the token if it may have leaked.                                                                                                                                  |
| Worker returns 429                         | Reduce cron frequency or owner-triggered flushes; honor the `Retry-After` response header.                                                                                                                              |
| Sentry source maps are not uploaded        | Confirm `SENTRY_ORG`, `SENTRY_PROJECT`, and `SENTRY_AUTH_TOKEN` exist only in build/CI secrets.                                                                                                                         |
